# 调查记录

材料为 `.materials/` 中的抖音与 Bilibili 保存页面、配套脚本和样式，以及提取的抖音模块 367931、623680、150486。轨道分配和 Canvas 合成采用 [Danmaku 上游实现](https://github.com/weizhenye/Danmaku)，锁定 npm 版本 2.0.9，捆绑脚本保留 MIT 许可。

## 已确认的代码路径

抖音原引擎使用 DOM 弹幕。业务 bulletCreateEl 为每条显示中的弹幕调用 React 渲染，包括文字、表情和点赞/举报/删除节点；组件还注册可见性和属性观察器。大量弹幕会增加 DOM、组件和观察器开销。

原引擎的移动与字号变化涉及位置读取、样式写入、暂停及重启。setFontSizeV1 反复 findIndex 查找待更新弹幕，updateQueueTimestamp 逐条读取位置并更新 transform/transition，存在随队列增长的布局处理成本。

业务在 SEEKING 清理缓存并 stop，SEEKED 时 clear/stop/start，然后异步加载网络批次。重建弹幕 DOM 与视频 seek 会争用主线程，但静态保存页面不足以确定某次卡顿的耗时占比。

Bilibili 保存页作为展示与渲染结构参考，不把“Bilibili 不卡”当作抖音卡顿原因的性能证明，也不复制其闭源引擎。

## 优化与限制

0.2.0 普通播放使用单 Canvas 合成。用户反馈它看起来比原版低帧率后，重新检查发现：虽然降低了 React 节点开销，但每帧清屏和 drawImage 都依赖主线程；原版 transform 则可以由合成线程推进。因此 Canvas 并不自动意味着动画更流畅。旧实现没有主动锁定 30 FPS，但页面长任务会延迟 RAF 和重绘；高分辨率、大量弹幕会进一步增加绘制工作。这是已确认的架构差异，尚不能仅凭代码断定用户现场每次掉帧的具体占比。浏览器对 transform 动画的加速机制见 [web.dev 官方说明](https://web.dev/articles/animations-overview)。

0.3.0 改为缓存 Canvas 位图 + Web Animations transform：仅新弹幕/内容变化时复制位图，位移交给浏览器。每条可见弹幕一个轻量位图节点，只有悬停弹幕挂载原生 React 子树。主线程负责约 32ms 一次的排队调度以及媒体时钟漂移校正，移动本身不锁定 30 FPS。缓存预算为 16 MiB，活跃节点另占位图及合成层内存；超高密度场景仍需关注 GPU 内存。

## 0.3.0 性能检查

`node tools/benchmark-realtime.mjs` 复用一个无头 Chrome，1920x1080 视口、DPR 2、4 倍 CPU 降速，5000 条输入，每组 8 秒模拟播放。若本地原始引擎存在，则加测原版。结果写入忽略提交的 output/。

复测三组运行结果：原版 104 条活跃弹幕；旧 Canvas 和新版均 130 条活跃，分别为 403 和 402 条排队。旧 Canvas 89280 次 drawImage、最慢调度 15.5ms；新版 130 次位图上传、最慢调度 9.7ms。两组 RAF 间隔 P95 均约 6.2ms。这说明绘制工作显著减少，但 RAF 间隔不是显示器实际呈现 FPS，而且原版和新版展示策略不同，不能换算成用户视频中的 FPS 提升倍数。

浏览器回归另验证：停止 JS 调度后位图动画继续移动，Chrome 图层诊断明确返回 ActiveTransformAnimation，确认实际启用了加速的 transform 动画。暂停/缓冲/倍速同步、跳转释放全部动画、普通动画帧不重复上传位图均通过；倍速在 animation.ready 后读取实际 playbackRate。原站实测访问停在验证码中间页，未尝试绕过，也没有记为线上通过。

本地测试覆盖真实浏览器绘制、接口契约、密集队列和跳转后状态。尚未采集相同真实视频、网络和设备条件的完整 DevTools 对照轨迹，因此不承诺具体提速比例，也不能消除解码、网络或其他插件造成的卡顿。

## 0.3.1 调度与兼容性

0.3.0 虽然每约 32ms 执行一次调度，仍在每个 RAF 中判断是否到期。0.3.1 改为独立定时调度，避免高刷新率下的空回调；无活跃弹幕时依据下一条时间延迟唤醒（最长 1 秒），新数据和倍速变更立即唤醒。等待轨道的队首弹幕复用测量结果，内容/字号/emoji 变化时失效。

集中到达的数据以 4ms 为调度工作的协作预算分批处理，余下内容留待下一次，不限制总条数。该预算不是整个回调的硬上限：单次位图创建、浏览器图层更新以及活动节点同步仍可能使总耗时超过 4ms。新批次到达、删除及服务器 ID 确认都会保留尚未读取的数据位置。

同条件直接对照命令：`BASELINE_REF=6613aad node tools/benchmark-realtime.mjs`。工具从 Git 读取旧版本源码到内存编译，不切换工作区。一次 8 秒、DPR 2、4 倍 CPU 降速测量中，0.3.0 为 1300 次 RAF 回调、222 次调度、累计调度 441.7ms、P95 6.9ms；0.3.1 为 216 次定时回调、217 次调度、累计 335.3ms、P95 5.9ms。两版均 130 条活跃和 130 次位图上传，排队分别 402/401 条（结束计时及最后一次调度存在边界差异）。本次累计调度下降约 24%，不等于用户实际 FPS 提升 24%，也不是跨设备的保证。

本轮同时修复缩放坐标、重排碰撞、底部轨道、重复服务器回包，以及动画重建后的倍速恢复。`npm run build` 通过，Chrome 和 Edge 各通过 42 项测试，测试浏览器退出后关闭。仍待验证：登录态真实视频性能轨迹、实际服务器操作、动态 emoji 帧动画和暂停发送的原站可见性。

## 0.3.2 跳转画面恢复

0.3.1 的 resetFrame 将 windowStart 设为目标时间，后续调度又将每条新显示弹幕的 time 改成当前时间。因此目标时间之前已入场、仍未离场的弹幕被过滤，画面只能等待新弹幕从右边进入。保存的业务模块还会在 SEEKING 将 main.data 置空，在 SEEKED 执行 clear/stop/start；只改读取起点不足以处理该流程。

0.3.2 在跳转期间保留当前实例的已加载时间轴，清除旧画面及积压任务。按当前持续时间设置与已知最长 duration 回溯候选，以原始发布时间设置动画进度；过期内容不恢复。使用上游分轨器按历史时间分配轨道，并检查目标时间的碰撞。异步回包也回溯补入，暂停时允许完成恢复工作。连续跳转取消旧恢复任务，关闭弹幕不会被跳转重新开启，媒体 emptied/销毁以及非跳转 clear 仍释放数据。

恢复按 4ms 协作预算分批，约 4ms 后接续，不等待正常播放的 32ms 检查间隔。先测量候选尺寸、分配轨道，仅为接受的弹幕创建位图。压力测试发现若预先给所有候选绘图，4 倍 CPU 降速下恢复约需 3.5 秒；延迟绘图后同场景约 0.7～1.1 秒，首批可见约 15～22ms。整个回调仍可能因绘图/图层提交超过协作预算。

可复测 `CPU_THROTTLE=1 node tools/benchmark-seek.mjs`：5000 条输入，1920x1080、DPR 2，依次跳到 60/30/65 秒并保持暂停。一次未降速测试中，首批可见为 19.9/12.7/13.8ms，全部候选处理完成为 78.7/86.5/74.9ms，最大单次 frame 为 8.4/9.1/12.3ms。每次恢复 182 条，778 条因轨道不足排队，左右半屏分别 104/78 条。测试输出只写入忽略提交的 output/。该数据不包含网络下载和视频解码时间，不代表实际设备上的固定延迟。

Chrome 和 Edge 各通过 50 项回归，包含恢复位置的动画计算值、截图、密集无重叠/不丢队列、延迟回包、关闭状态、倍速及 emoji/透明度/悬停，以及播放中原站重启后的继续移动与过期清理。目标所需历史既未缓存也未由原站返回时无法完整恢复；原站按 32 秒分段取数，靠近未缓存分段起点时尤其受此限制。真实网站登录态对照仍待完成。

## 0.3.3 密集跳转与倍速抖动

0.3.2 会在每个恢复批次结束后立即显示刚准备好的弹幕，因此大量候选会逐批冒出。动画同时把浏览器最近一次渲染采样的 currentTime 与视频当前时间相减，偏差超过 100ms 就硬改动画进度。主线程忙碌或视频时间采样较粗时，两者的采样时刻不同；倍速会放大偏差，反复校正可造成前后跳动。重复设置相同 duration 也会多余地改变动画起点。

0.3.3 在隐藏状态下准备位图与节点，候选处理完成后统一发布；晚到的网络批次单独准备，已有动画继续移动。发布前补入准备期间经过的时间段。位图上传纳入每批 4ms 协作预算，用 MessageChannel 接续可取消的任务，避免嵌套短定时器钳制；已准备的隐藏节点不反复同步。暂停重建仍完成，停止/销毁取消任务，替换式回包重新调度尚未准备的条目。

动画使用同一次 performance.now 采样建立 startTime，常规播放不再循环写 currentTime。倍速变更保留当前动画进度；真正跳转、暂停/恢复、几何或起点变化仍同步状态。悬停与变速读取实际动画位置，相同 duration 不重置起点。真实 WebM 视频与粗粒度模拟时钟的 2x/4x 回归覆盖忙碌主线程下的位置单调性、重复设置、暂停、缓冲及冻结。

5000 条输入、1920x1080、DPR 2、4x 播放，依次跳到 60/30/65 秒：一次未降速运行恢复用时 50.6/60.2/70.5ms，未完成画面可见次数均为 0；同条件读取 Git 中 0.3.2 的对照为 76.4/65.8/86.9ms，未完成画面可见次数为 6/5/6。4 倍 CPU 降速的一次运行恢复为 571.5/444.6/553.4ms，也未出现分批可见。极端压力下单次回调仍可能超过预算，本次最大值约 61ms，不能视为已消除所有长任务。

复测命令为 `CPU_THROTTLE=1 PLAYING=1 PLAYBACK_RATE=4 node tools/benchmark-seek.mjs`，增加 `BASELINE_REF=f2b33c2` 可读取旧版本直接对照，无需切换工作区。工具记录分批可见次数和耗时分项，日志及截图只留在忽略提交的 output/。这些数据来自本地夹具，不含网络请求和视频解码的耗时，也不代表显示器实际呈现 FPS 或登录态抖音验收。

0.3.3 构建通过，Chrome 与 Edge 各通过 59 项回归，包含真实视频 2x/4x、密集恢复整体显示、重建追帧、暂停完成、任务取消及替换回包不丢数据。测试浏览器均在结束后关闭。
